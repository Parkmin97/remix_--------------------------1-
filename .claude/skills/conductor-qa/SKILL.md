# Conductor QA

"존재 확인"이 아니라 **"경계면 정합성"**을 검증한다. 모듈 완성마다 점진적으로 돌린다.

## 검증 절차
1. **빌드/타입**: `npx tsc --noEmit` → 에러 0 확인. `npm run build` → 성공 확인.
2. **경계면 교차 비교** (핵심 — 파일을 동시에 열어 shape 비교):
   - `types.ts` 인터페이스 ↔ 소비 컴포넌트/훅의 실제 사용
   - `App.tsx`가 넘기는 props ↔ 각 화면 컴포넌트의 props 시그니처
   - 곡 데이터 `bpm`/`beatType` ↔ 미션 판정 로직의 가정
   - 저장소 저장/로드 shape ↔ `SessionData`/`DailyReport`
3. **회귀**: landing → phone-home → mission → self-reflection → report 전환 경로가 살아있는지 정적 추적.
4. **런타임 스모크**(가능 시): 브라우저로 랜딩·미션 로드, 콘솔 에러 유무 확인.

## 리포트 형식
FAIL 항목마다: `{ 파일:라인 | 증상 | 재현 조건 | 예상 vs 실제 | 담당 에이전트 }`.
PASS면 검증한 경계면 목록을 한 줄씩 남긴다.

## 규칙
- 코드를 직접 수정하지 않는다. 수정은 소유 에이전트의 책임.
- 빌드 로그는 추측 없이 원문으로 전달.
- 센서 권한 거부·오디오 폴백은 "정상 폴백"이지 실패가 아니다 — 구분해서 판단.

## 왜 이렇게 하나
실제 버그의 대부분은 개별 파일이 아니라 파일 사이(경계면)에서 발생한다. API 응답 shape과 프론트 훅의 기대가 어긋나는 식이다. 그래서 한 파일만 보지 않고 양쪽을 동시에 읽어 비교한다. 모듈마다 즉시 검증하는 이유는, 끝에 몰아서 하면 어느 변경이 깨뜨렸는지 특정하기 어렵기 때문이다.
